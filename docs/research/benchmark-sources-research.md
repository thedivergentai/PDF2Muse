# Benchmark Sources Research

Research task: identify practical clean printed/typeset benchmark sample sources that PDF2Muse can legally use or generate locally for Phase 1 completion-roadmap work.

## 5-Bullet Summary

- Use repo-owned synthetic samples as the Phase 1 seed set: generate simple MusicXML scores, render clean PDFs locally with MuseScore or LilyPond, and commit only small fixtures with clear provenance.
- Use OpenScore Lieder and OpenScore String Quartets as the primary external clean-typeset source because the source score repositories are CC0 and provide MuseScore files that can be batch-exported to PDF and MusicXML.
- Use the MIT-licensed MusicXML test suite for targeted notation-feature snippets, not as a repertoire benchmark, because it is designed to test MusicXML rendering behavior.
- Treat Mutopia and Humdrum/KernScores as useful secondary sources only after per-file license/provenance checks; both can provide clean renderings, but licensing and source-status details vary by file.
- Keep full corpora, downloaded PDFs, generated run outputs, IMSLP scans, and license-uncertain datasets local; commit manifests, source-generation scripts, small redistributable samples, and license/attribution notes only when rights are explicit.

## Recommended Source Strategy

Phase 1 should optimize for repeatability and legal clarity over scale.

1. **Seed with local synthetic clean-typeset fixtures.**
   Create a small set of repo-owned MusicXML scores that exercise the current PDF2Muse path: single-staff melody, grand staff piano, SATB chorale, simple multi-part score, lyrics, repeats, key/time changes, tuplets, and page breaks. Render PDFs locally with MuseScore CLI, using the same source MusicXML as ground truth.

   This gives the project a stable smoke set with no upstream dataset ambiguity. It should not be presented as an accuracy benchmark; it is a regression and pipeline sanity set.

2. **Add a curated OpenScore clean-typeset benchmark.**
   OpenScore Lieder and OpenScore String Quartets are the best practical external sources. Their GitHub repositories are CC0, provide MuseScore source files, and document batch conversion through MuseScore command-line jobs. Select a small, diverse subset first, then generate PDFs and MusicXML locally from the same source files.

   Recommended Phase 1 subset:
   - 10 short OpenScore Lieder songs for voice/piano, lyrics, and grand-staff accompaniment.
   - 5 short string-quartet movements or page ranges for four-part ensemble layout.
   - Prefer first-page or one-to-two-page samples until CPU runtime and report review are manageable.

3. **Use the MusicXML test suite as targeted feature coverage.**
   The unofficial MusicXML test suite is MIT licensed and explicitly permits use if the license notice is kept intact. It is useful for small feature probes such as clefs, accidentals, chords, tuplets, repeats, slurs, articulations, lyrics, and layout edge cases. Use it as a feature fixture source, not as a musical quality benchmark, because the rendered output can reflect renderer-specific interpretation.

4. **Defer Mutopia and Humdrum/KernScores to curated local candidate pools.**
   Mutopia is practical because it provides LilyPond source and rendered PDFs, but each piece carries its own Public Domain, CC BY, or CC BY-SA license. Humdrum/KernScores is large and convertible, with many public-domain-oriented sources, but some access paths and linked PDFs have mixed provenance or restrictions. These are good expansion sources once each sample records a per-file license decision.

5. **Avoid Phase 1 dependence on license-uncertain packaged OMR datasets.**
   Existing OMR datasets can be valuable later, but Phase 1 clean-typeset benchmarking should not depend on datasets where redistribution terms, underlying score rights, or packaging terms are unclear. Use those only as local exploratory material until rights are verified.

## Practical Candidate Sources

### Repo-Owned Synthetic MusicXML

- **Use case:** Small committed fixtures and smoke benchmarks.
- **Inputs:** MusicXML generated by hand, music21, MuseScore, or a small project script.
- **PDF generation:** MuseScore CLI, for example `MuseScore4.exe -o score.pdf score.musicxml`.
- **Ground truth:** The source MusicXML.
- **License posture:** Project-owned if authored in-repo; easiest source for committed samples.
- **Risk:** Too artificial to support quality claims. Label as smoke/regression coverage.

### OpenScore Lieder

- **Source:** `OpenScore/Lieder` GitHub repository and related OpenScore Lieder corpus pages.
- **Formats:** MuseScore source files, with documented export to PDF, MusicXML/MXL, MIDI, and related formats.
- **License posture:** Repository is CC0-1.0; project docs state scores are released under Creative Commons Zero.
- **Use case:** Primary clean printed/typeset external benchmark source.
- **Risk:** If downloading from MuseScore.com or other mirrors, record the exact source URL and keep the CC0 repository license with the sample. Do not assume third-party packaged derivatives inherit identical terms.

### OpenScore String Quartets

- **Source:** `OpenScore/StringQuartets` GitHub repository.
- **Formats:** MuseScore files and associated data, with documented export to PDF and MusicXML.
- **License posture:** Repository is CC0-1.0; project asks for credit in public-facing use.
- **Use case:** Multi-staff ensemble clean-typeset benchmark samples.
- **Risk:** Some derived Hugging Face datasets and OMR packages based on this corpus use different licenses, such as CC BY 4.0. Prefer the original GitHub source for Phase 1.

### MusicXML Test Suite

- **Source:** LilyPond/cuthbertLab unofficial MusicXML test suite.
- **Formats:** MusicXML snippets; render locally to PDF with MuseScore or LilyPond.
- **License posture:** MIT license; keep copyright/license notice.
- **Use case:** Feature-targeted fixtures for notation elements that are hard to cover through repertoire alone.
- **Risk:** Not a natural repertoire benchmark. Renderer differences can affect the visual input, so record renderer and version.

### Mutopia Project

- **Source:** Mutopia Project LilyPond files and rendered PDFs.
- **Formats:** PDF, MIDI, LilyPond source.
- **License posture:** Per-piece Public Domain, CC BY, or CC BY-SA; each piece lists its own license.
- **Use case:** Secondary source for clean LilyPond-engraved public-domain repertoire.
- **Risk:** ShareAlike obligations can attach to modified derivatives, and attribution is required for CC BY/CC BY-SA. Only commit files after recording the exact per-piece license and required attribution.

### Humdrum/KernScores

- **Source:** KernScores / Humdrum `**kern` data.
- **Formats:** Humdrum source; can be converted to MusicXML with `hum2xml` or rendered via Verovio/MuseScore workflows.
- **License posture:** Many sources are public-domain-oriented, but access and provenance vary by collection/file.
- **Use case:** Later expansion for symbolic ground truth and historically diverse repertoire.
- **Risk:** Some materials are copyright restricted or linked to scanned PDFs with separate status. Keep local until each selected file has a documented rights decision.

## Licensing Risks

- **Underlying composition vs digital engraving:** Public-domain compositions do not automatically make a modern engraving or transcription redistributable. Track both the musical work and the encoded/rendered edition.
- **Mirror and derivative drift:** A CC0 source corpus can appear in derived packages under CC BY or other terms. Use original source repositories when possible and record the exact source.
- **MuseScore.com terms:** Prefer OpenScore GitHub sources over ad hoc MuseScore.com downloads. If a sample comes from MuseScore.com, verify the individual score license and site terms before committing.
- **IMSLP scans:** IMSLP can be useful for later scanned/historical evaluation, but it is not the clean-typeset Phase 1 target and regional public-domain status can vary.
- **Renderer-generated artifacts:** PDFs rendered from third-party source files inherit the source-file licensing obligations. Record the renderer version for reproducibility, but the renderer license normally does not make the generated score proprietary.
- **Generated synthetic data claims:** Locally generated samples are legally clean but can overstate real-world performance. Reports should describe them as smoke/regression fixtures.

## Concrete Sample Layout

Keep full datasets and generated outputs local by default:

```text
datasets/
  benchmark-sources/
    clean-typeset/
      synthetic/
        satb-chorale-001/
          source.musicxml
          input.pdf
          metadata.json
      openscore-lieder/
        schumann-op12-no4-page1/
          source.mscx
          ground_truth.musicxml
          input.pdf
          LICENSE.txt
          metadata.json
      openscore-string-quartets/
        example-quartet-page1/
          source.mscx
          ground_truth.musicxml
          input.pdf
          LICENSE.txt
          metadata.json
```

Recommended per-sample `metadata.json`:

```json
{
  "id": "openscore-lieder-schumann-op12-no4-page1",
  "title": "Liebst du um Schonheit",
  "composer": "Clara Schumann",
  "source_url": "https://github.com/OpenScore/Lieder",
  "source_commit": "record exact commit or release tag",
  "source_format": "mscx",
  "renderer": "MuseScore Studio",
  "renderer_version": "record locally",
  "license": "CC0-1.0",
  "license_notes": "OpenScore Lieder source repository states scores are CC0; retain LICENSE.txt.",
  "difficulty_tags": ["clean-typeset", "lyrics", "voice-piano", "grand-staff"],
  "pages": [1]
}
```

Recommended evaluation manifest shape:

```json
{
  "samples": [
    {
      "id": "openscore-lieder-schumann-op12-no4-page1",
      "input": "../../datasets/benchmark-sources/clean-typeset/openscore-lieder/schumann-op12-no4-page1/input.pdf",
      "ground_truth": "../../datasets/benchmark-sources/clean-typeset/openscore-lieder/schumann-op12-no4-page1/ground_truth.musicxml",
      "source": "OpenScore Lieder",
      "license_notes": "CC0-1.0; generated locally from OpenScore source with MuseScore Studio.",
      "difficulty_tags": ["clean-typeset", "lyrics", "voice-piano", "grand-staff"],
      "first_page": 1,
      "last_page": 1
    }
  ]
}
```

Use stable sample IDs that encode source, work, and page range. Keep page-limited samples explicit because PDF2Muse CPU OMR runs can be slow.

## What Can Be Committed

- This research artifact.
- Small repo-owned synthetic MusicXML/PDF fixtures once they are intentionally generated for tests and documented as project-owned.
- Small CC0 OpenScore-derived samples if each committed sample includes license text, source URL, source commit/release, and generation metadata.
- MIT MusicXML test-suite snippets if the MIT license notice is retained and the fixture purpose is feature coverage.
- Example manifests that point to local paths, with no expectation that raw datasets are present.
- Scripts or documented commands that reproduce local generation from legal sources.

## What Should Stay Local

- Full cloned corpora, full rendered OpenScore exports, and bulk benchmark runs.
- Downloaded datasets whose redistribution rights have not been checked file by file.
- IMSLP scans and other historical PDFs unless regional copyright status and source terms are recorded.
- Mutopia samples with CC BY/CC BY-SA obligations until attribution and derivative-sharing requirements are explicitly handled.
- Humdrum/KernScores selections until each file's source and access status are documented.
- `evaluation/runs/`, generated OMR outputs, and any large rendered PDF/image batches.

## Phase 1 Recommendation

Build the first clean-typeset benchmark in three rings:

1. **Ring 0:** 8-12 synthetic, repo-owned smoke samples committed as small fixtures.
2. **Ring 1:** 15-30 local OpenScore samples from Lieder and String Quartets, rendered locally and referenced by `evaluation/manifests/clean-typeset.local.json`.
3. **Ring 2:** Optional feature probes from the MIT MusicXML test suite, committed only when a specific notation behavior needs a stable regression fixture.

This gives PDF2Muse a legally clear, reproducible Phase 1 benchmark path while avoiding unsupported quality claims and avoiding redistribution of uncertain datasets.
